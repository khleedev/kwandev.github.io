가상의 서비스에서 10월 24일 새벽 2시부터 가격을 10,000원에서 12,000원으로 올린다고 해봅시다. 코드를 미리 배포하고 요청 시각에 따라 가격을 선택하면, 변경 시각에 따로 배포할 필요가 없습니다.

변경 시각과 새 가격이 확정되고, 전환 후에는 기존 가격으로 돌아갈 필요가 없는 경우를 다룹니다.

이 코드를 작성하는 방법은 두 가지입니다.

- 기존 가격 10,000원을 기본 데이터에 저장하고, 변경 시각부터 12,000원으로 덮어써서 반환합니다.
- 새 가격 12,000원을 기본 데이터에 저장하고, 변경 시각 전까지만 10,000원으로 덮어써서 반환합니다.

두 방식 모두 변경 전에는 10,000원, 변경 시각부터는 12,000원을 반환합니다. **기본값은 조건에 따라 덮어쓰기 전의 기본 데이터**를 뜻합니다.

차이는 가격 변경이 끝나고 날짜 조건을 정리할 때 생깁니다. 첫 번째 방식은 기본 데이터도 12,000원으로 고쳐야 합니다. 두 번째 방식은 이미 새 가격이 저장되어 있으므로, 기존 가격과 그 가격을 반환하던 조건문을 제거하면 됩니다.

## 지금 가격을 기본값으로 두는 코드

두 예제 모두 서버에서 받은 유효한 `Date` 값을 사용한다고 가정합니다.

```ts
const SWITCH_AT = new Date("2026-10-24T02:00:00+09:00").getTime();

const PRICES = { basic: 10000 };
const PRICES_AFTER = { basic: 12000 };

function getPrices(now: Date) {
  if (now.getTime() < SWITCH_AT) return PRICES;
  return { ...PRICES, ...PRICES_AFTER };
}
```

전환 전에는 `PRICES`를 반환합니다. 전환 시각부터는 `PRICES`의 값을 `PRICES_AFTER`의 값으로 대체한 새 객체를 반환합니다. 원본 `PRICES`는 수정하지 않습니다.

전환 후에도 `PRICES`에는 예전 가격이 남습니다. 정리할 때는 `PRICES`를 새 가격으로 바꾼 뒤 날짜 비교와 `PRICES_AFTER`를 지워야 합니다.

## 바뀐 가격을 기본값으로 두기

`PRICES`에 새 가격을 저장합니다. 전환 전까지만 `PRICES`의 값을 `PRICES_BEFORE`의 값으로 대체한 새 객체를 반환하고, 원본 `PRICES`는 수정하지 않습니다.

```ts
const SWITCH_AT = new Date("2026-10-24T02:00:00+09:00").getTime();

const PRICES = { basic: 12000 };
const PRICES_BEFORE = { basic: 10000 };

function getPrices(now: Date) {
  if (now.getTime() < SWITCH_AT) {
    return { ...PRICES, ...PRICES_BEFORE };
  }
  return PRICES;
}
```

기본 데이터를 직접 읽으면 전환 전에 새 가격이 노출될 수 있으므로, 모든 사용처가 `getPrices`를 거치는지 확인해야 합니다.

두 코드의 반환 값은 같습니다. `+09:00`은 한국 시간 기준이며, 전환 시각부터 새 가격을 반환합니다.

각 예제의 `getPrices`를 정의한 뒤 아래 코드로 반환 값을 확인할 수 있습니다.

```ts
getPrices(new Date("2026-10-24T01:59:59.999+09:00"));
// { basic: 10000 }

getPrices(new Date("2026-10-24T02:00:00+09:00"));
// { basic: 12000 }
```

| 요청 시각       | basic |
| --------------- | ----- |
| 전환 1밀리초 전 | 10000 |
| 전환 시각       | 12000 |
| 전환 1밀리초 후 | 12000 |

전환 후 `SWITCH_AT`, `PRICES_BEFORE`, 전환 전 분기를 지우면 다음 코드가 남습니다.

```ts
const PRICES = { basic: 12000 };

function getPrices() {
  return PRICES;
}
```

`PRICES`를 다시 수정할 필요가 없습니다. 함수에서 시간 인자도 제거한다면 호출부와 테스트를 함께 수정합니다.

## 임시 코드에는 지울 시점도 필요하다

날짜 분기를 추가할 때 정리 시점도 정해둡니다. 가격 변경 다음 날 정리한다면 기존 가격과 날짜 분기를 제거하고, 새 가격이 반환되는지 확인합니다.

전환 전 가격을 기대하는 테스트와 사용하지 않는 상수도 함께 정리합니다.

설정값에 따라 실행할 동작을 선택하는 기능 플래그도 정리가 필요합니다. 역할이 끝난 분기가 남아 있으면 코드를 수정할 때 불필요한 경로까지 검토해야 합니다.

Uber는 역할이 끝난 기능 플래그와 관련 코드를 자동으로 제거하는 도구 [Piranha](https://www.uber.com/blog/piranha/)를 만들었습니다.

## 전환이 확정된 코드에 적용하기

이 방식은 전환 날짜와 최종 상태가 확정되고, 이전 상태를 유지할 필요가 없을 때 적용합니다. 실험, 장애 대응, 과거 시점 조회에 필요한 코드는 별도의 제거 기준이 필요합니다.

카카오톡 친구 탭 개편은 되돌릴 가능성을 생각해볼 수 있는 사례입니다. 카카오는 2025년 9월 친구 탭을 피드형으로 바꿨다가, 이용자 반발 이후 같은 해 12월 16일부터 친구 목록을 기본 화면으로 다시 제공하는 업데이트를 순차 진행했습니다. 피드형 화면은 '소식' 옵션으로 남겼습니다. ([한국일보 보도](https://www.hankookilbo.com/news/article/amp/A2025121615360002957))

카카오 내부의 기능 플래그 사용 여부나 코드 구조는 이 보도로 알 수 없습니다. 이 사례에서 참고할 점은 출시 후에도 유지할 동작이 바뀔 수 있다는 것입니다. 사용자 반응을 확인해야 하는 개편이라면, 이전 동작을 유지할 기간과 되돌릴 조건을 먼저 정해야 합니다.
