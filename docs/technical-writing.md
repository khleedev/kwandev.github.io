# 테크니컬 라이팅 지침

이 프로젝트에서 기술 글을 쓰거나 검토할 때 사용하는 기준이다. 독자가 필요한 내용을 이해하고 직접 적용할 수 있도록 문서 유형, 구조, 문장 순서로 점검한다.

[테크니컬 라이팅 가이드](https://technical-writing.dev/)의 원칙을 요약·재구성하고, 아래에 별도로 표시한 프로젝트 규칙을 추가했다. 원문의 권장 사항을 글의 목적에 맞게 적용하며, 모든 글을 같은 목차나 말투로 바꾸지는 않는다.

## 1. 독자와 문서 유형 정하기

초안을 쓰기 전에 예상 독자, 필요한 사전 지식, 읽고 나서 할 수 있어야 하는 일을 각각 한 문장으로 정리한다. 기존 글을 고칠 때는 본문에서 먼저 파악하고, 결과를 크게 바꿀 정보가 없을 때만 질문한다.

가장 중요한 독자 목표를 기준으로 다음 구성을 선택한다. 필요 없는 절은 생략하고, 다른 목적의 긴 설명은 별도 글이나 링크로 연결한다.

| 유형      | 독자의 목표                      | 구성의 출발점                                                      |
| --------- | -------------------------------- | ------------------------------------------------------------------ |
| 학습      | 처음부터 따라 하며 배우기        | 완성할 결과 → 준비 환경 → 순서대로 실습 → 결과 확인                |
| 문제 해결 | 특정 오류를 고치거나 작업 끝내기 | 증상·목표 → 적용 조건 → 해결 절차 → 정상 동작 확인 → 원인·제약     |
| 참조      | 필요한 명세를 빠르게 찾기        | 용도 → 시그니처 → 입력 타입·필수 여부·기본값 → 반환 값·오류 → 예제 |
| 설명      | 개념과 원리를 이해하기           | 핵심 개념 → 등장 배경 → 동작 원리 → 사례·비교 → 한계               |

출처: [문서 유형 정하기](https://technical-writing.dev/type/index.html), [기본 문서 작성하기](https://technical-writing.dev/tutorial/basic-documents.html).

## 2. 읽는 순서 설계하기

- 한 글의 핵심 질문을 하나로 좁힌다. 독립적인 목표가 섞이거나 H4 이상으로 깊어지면 글을 나눌지 검토한다.
- 도입에서 해결할 문제와 얻을 결과를 먼저 알려준다. 긴 배경과 부가 정보는 뒤로 보낸다.
- 제목에 기술명과 구체적인 작업·개념을 담는다. 30자 안팎을 목표로 하되, 길이를 줄이려고 의미를 버리지 않는다.
- 소제목만 읽어도 흐름을 알 수 있게 쓴다. 같은 수준의 제목은 비슷한 형식을 유지한다.
- 준비가 필요한 작업은 준비 사항부터 안내한다. 절차는 실행 순서대로, 설명은 기초 개념부터 배치한다.
- 새 개념은 처음 나올 때 짧게 정의한다. 입력·상태·환경에 따라 동작이 달라지면 그 조건도 설명한다.

출처: [정보 구조 만들기](https://technical-writing.dev/architecture/index.html), [자세히 설명하기](https://technical-writing.dev/architecture/background.html).

## 3. 문장 다듬기

- 한 문장에는 핵심 생각 하나를 담는다. 반복, 과장, 내용 없이 글의 진행만 예고하는 표현은 덜어낸다.
- 작업 안내는 독자가 할 행동을 동사로 쓴다. 시스템 자체의 동작을 설명할 때는 시스템을 주어로 써도 된다.
- 가능하면 능동형을 쓴다. 예: “설정 변경이 요구됩니다” → “설정을 변경하세요.”
- “적절히”, “빠르게” 대신 조건·값·단위를 제시한다. 확인할 수 없는 수치나 성능 효과를 만들어 넣지는 않는다.
- 불필요한 한자어와 번역체를 줄인다. 예: “설정의 변경을 수행합니다” → “설정을 변경합니다.”
- 공식 기술명과 대소문자를 지킨다. 같은 개념은 같은 용어로 부르고, 약어는 첫 등장에 뜻을 설명한다.
- 외래어는 독자에게 익숙한 표기를 선택한다. 문체는 저자의 목소리를 유지하면서 문서 안에서 자연스럽게 맞춘다.

출처: [문장 다듬기](https://technical-writing.dev/sentence/index.html), [문장의 주체를 분명하게 하기](https://technical-writing.dev/sentence/subject.html), [일관되게 쓰기](https://technical-writing.dev/sentence/consistency.html).

## 4. 프로젝트에 적용하기

이 절은 원문의 규칙과 구분되는 프로젝트 운영 규칙이다.

- 기술 글은 `src/content/blog/`, 개인 기록은 `src/content/notes/`의 기존 분류와 파일명 관례를 따른다.
- frontmatter는 `src/content.config.ts`를 기준으로 한다. 블로그에는 `title`, `description`, `date`가 필요하고, 노트는 `description`을 생략할 수 있다. 두 컬렉션 모두 `draft`, `tags`는 선택 사항이다.
- 새 블로그 글의 `description`에는 독자가 얻을 내용을 짧게 요약한다. 독자나 문서 유형을 저장하기 위한 새 필드는 추가하지 않는다.
- 게시글 제목은 페이지가 H1으로 출력하므로 새 글의 본문은 H2부터 구성한다. 기존 글의 제목 구조는 수정 범위에 포함될 때 정리한다.
- 코드 블록에 언어를 표시한다. 실행 예제에는 필요한 import, 파일 위치, 명령어, 예상 결과를 제공한다. 일부 코드라면 생략한 부분을 밝힌다.
- 버전에 따라 달라지는 설명은 적용 버전과 공식 출처를 적는다. 사실, 개인 경험, 추정은 구분하고, 저자의 경험이나 검증 결과를 지어내지 않는다.
- 설명하는 링크 텍스트와 이미지 대체 텍스트를 쓴다. 표는 비교에, 번호 목록은 실행 순서에 사용한다.
- 글 검토는 유형 → 구조 → 문장 순서로 진행한다. 피드백은 `위치 / 문제 / 독자에게 미치는 영향 / 수정 예시`로 제시한다.

## 5. 완료 전 체크리스트

- [ ] 독자와 글의 목표가 분명하고, 목적에 맞는 유형을 선택했는가?
- [ ] 제목과 도입만 읽어도 얻을 내용을 알 수 있는가?
- [ ] 한 글이 하나의 핵심 목표에 집중하며, 소제목의 흐름이 자연스러운가?
- [ ] 준비 사항, 새 개념, 동작 조건을 독자가 추측하지 않아도 되는가?
- [ ] 절차와 예제에 결과 확인 방법이 있는가? 실행 여부를 정확히 밝혔는가?
- [ ] 모호한 표현, 반복, 불필요한 번역체를 줄였는가?
- [ ] 기술명·약어·용어·문체가 일관되고, 주장의 근거를 확인했는가?
- [ ] frontmatter, 코드 블록, 링크, 이미지 설명이 프로젝트 형식에 맞는가?

개인 기록이나 짧은 수정에는 해당하는 항목만 적용한다. 콘텐츠 형식이나 MDX 구문을 바꿨다면 `pnpm build`로 확인한다. 빌드 성공은 글의 사실관계나 예제 실행을 검증한 결과와 구분한다.
